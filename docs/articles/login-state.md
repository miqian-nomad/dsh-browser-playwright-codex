# 让 AI 用你**已经登录的**账号干活（DSH 浏览器插件的登录态怎么做的）

> 长尾定位：搜「deepseek harness 用已登录账号」「dsh 浏览器 登录」的人，找的是这件事。
> 结论先行：插件的窗口带**独立 profile**，你手动登录一次；关窗/重启后，**持久 cookie 在 profile 里，
> 会话 cookie 靠一份导出的状态文件回注** —— 所以「下次还在登录状态」不是靠运气。

## 为什么这件事不好做

浏览器里有两类登录凭证，寿命完全不同：

| 类型 | 例子 | 关掉浏览器后 |
|---|---|---|
| 持久 cookie | `max-age` 很长的登录凭证 | **还在**（存在 profile 目录里） |
| **会话 cookie** | 大多数后台的 session | **没了**（Chrome 关窗即丢） |

所以「登录一次一直记得」的难点**全在第二类**。很多自动化方案每次开一个全新 context，等于每次都要重登；
或者干脆用了你的日常浏览器，把自动化行为混进你的个人会话里。

## 我们的做法（两句话）

1. **独立 profile 目录**（`~/.dsh/browser-profiles/playwright`）：你在这个窗口里登录一次，持久部分天然留下；
   它也和你日常浏览器**互不干扰**。
2. **会话 cookie 靠导出/回注**：关窗前把 cookie + localStorage 导到一份状态文件；下次启动时注入回去。
   这就是「重启 DSH 之后还是登录状态」的原因。

## 一个容易被忽略的细节：导出本身会**开一个临时页面**

Playwright 的 `storageState()` 有个行为：为了覆盖「没有打开页面」的 origin，它会**开一个临时页面**再导航过去。
在**有头**模式下，这会**把窗口从最小化拽到你眼前** —— 对「让 AI 在后边安静干活」是致命的。

我们在源码里处理了这点：窗口处于最小化时，**跳过完整导出、只取 cookies**（够用），而不是为了导出把窗口弹出。
完整根因与实测见 [`FOCUS-STEALING.md`](../../FOCUS-STEALING.md)。

## 你怎么复核（不用信我）

```sh
# 装
dsh plugin --profile web add github:miqian-nomad/dsh-browser-playwright-codex

# 验收：57 项自包含检查，不需要 DSH、不需要联网（自带本地测试服务器）
npm run verify

# 环境体检：宿主包导出是否还对得上
npm run doctor
```

- 登录态相关的回归在 `tests/login-state.test.ts`（含「窗口最小化时也必须刷新状态」的守卫，
  它**换回旧代码会挂** —— 这是它值得存在的原因）。
- 安全边界（能读什么、绝不能做什么）写在 [`SECURITY.md`](../../SECURITY.md)：**它不会替你输密码或验证码**，
  遇到登录/验证码会停下来把页面交还给你。

## 边界：它不做什么

- **不伪造指纹**。只做减法（摘掉 `--enable-automation` 等），因为伪造反而会造出一个不存在的设备。
- **不偷偷重登**。需要登录时它停住、上报、等你 —— 而不是拿你的账号去猜密码。
- **不跨站乱跑**。`allowedDomains` 配了就锁；五条能导航的路径全部在动作投递前校验。
